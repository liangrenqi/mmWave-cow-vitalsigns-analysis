# H10 并入雷达采集验证 V2：雷达与 H10 并行互不干扰（测前写定）

写于 2026-10-08，V2 采集之前，H10 并入代码部署之前。
- 代码：`wireless/h10_session.py`（新）、`h10_logger.py`（加重连 / 删绑定 / 看护父进程 / 退出兜底）、`capture_linux.py`（接入）。
- 判定脚本：`vitalsigns_analysis/h10_v2_check.py`。它只执行本文件，不改判据。

V2 只回答一件事：**雷达与 H10 同段并行时，两边各自的数据是否都完好，H10 的生命周期是否与段一一对应**。

判据 3（RR 与 ECG 逐拍）按用户 09-30 决定从 V2 拆出，不进 V2 判定。V2 数据是判据写定后的新数据，判据 3 照 `H10_判据3对齐_合并方案AB_测前写定.md` **单独判一次**，结果单列。这也是合并方案 AB 第一次真正的验证。

## 条件

- 部署前先 diff 远端，部署后核 md5。全程用新代码，不加诊断参数。
- 佩戴 H10，电极湿润，**静坐不动**，距雷达 0.5–1 m。手机蓝牙关闭，Pi WiFi 用 5 GHz。
- 用 `capture_linux.py` 采 **3 段**，每段采当前波形 5 分钟。终端前台跑，暂不经 systemd，那是 V3。
- 不人为断开 H10。重连在 V2-R 单独测。

## 结论

| 3 段 | 结论 |
|---|---|
| 全部通过 | V2 通过 → 进入 V2-R（重连）与 V3（systemd） |
| 有段 V2-1 不满足 | **最严重**：H10 拖累了雷达。先对照不开 H10（`--no-h10`）的同条件段，判断是不是 H10 引起的 |
| 有段 V2-4 或 V2-5 不满足 | 雷达或 USB 3 / 以太网可能干扰了 BLE。记下，先用 `--no-h10` 之外的手段查原因（btmon、RSSI），不放宽阈值 |
| 仅 V2-6 / V2-7 不满足 | 生命周期问题，修代码后重做 V2，不必重新写定判据 |
| 仅 V2-9 不满足 | 音频映射或 wav 文件问题，修后重做 |

## 单列：判据 3（合并方案 AB）

对 3 段的 H10 日志各跑一次 `h10_rpeak.py <日志>`（判定模式），输出「通过 / 不通过 / 无法判定」。
- 3 段都「通过」：合并方案 AB 在新数据上第一次得到验证。
- 任一段不是「通过」：报告用户，不改算法重跑。

无论哪种结果，**都不影响 V2 结论**。

## V2-R：断线重连（V2 通过后再做，另 2 段）

- 段 R1：采集开始约 60 s 后，在另一个 ssh 会话执行 `bluetoothctl disconnect 24:AC:AC:11:CC:D4`，由主机侧强制断开。这一步是确定可复现的。
- 段 R2：采集开始约 60 s 后，佩戴者走到 BLE 范围之外，约 15 m 并隔墙，停留 30 s 后回来。这一步是真实场景。

判据：
- 雷达 `verdict=GOOD`。
- 日志中 `disconnected` 的次数等于人为制造的断开次数，之后有新的 `connected`，且新连接之前有 `bond_remove rc=0`。
- 从断开到重连后首个 PMD 帧：R1 ≤ 30 s。R2 是从回到范围内起算 ≤ 30 s，回到范围内的时刻由人工记录。
- meta 中 `h10_status=DROPOUT`，`h10_unexpected_disconnects` 等于人为断开次数。
- 依次听到「心率带断开」「心率带已重连」各一次。

## 这套验证证明不了什么

- 只覆盖人体、静坐、室内。牛场的距离、遮挡、金属围栏，以及牛的动作，都要到现场再测。
- 「雷达不受影响」只用七项判据验证，判据之外的性能（如 CPU 余量）未测。
- 服务环境（User=pi、systemd）下的删绑定权限由 V3 回答，V2 不回答。
