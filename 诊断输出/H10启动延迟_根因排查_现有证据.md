# H10 PMD 启动约 30 s 延迟：根因排查（现有证据，2026-09-28）

工具：`h10_btsnoop_timeline.py`（全部 8 份 btsnoop 的逐包时间线 → `H10_btsnoop时间线_全部.md`）、
`h10_export_start_gap.py`（手机导出 → `H10手机导出_启动延迟估计.md`）。原始文件只读。

## 1. 手机导出里有没有这 30 s：**导出回答不了**

- 导出的 ECG/ACC/HR/GPS 四个文件，MS 列各自从约 0 起算，文件头只有秒级时刻，**没有「启动命令」时刻**，无法算「启动 → 首帧」
- 间接估计（均为推断，依赖未核实假设）：ECG 起点约在记录开始后 9.7 s（末端对齐）或 12.8 s（HR 轴对齐）。两者不一致，都 < 30 s 但不是 0
- 更关键的是：App 可能在按「开始记录」之前就已连接并在推流，那样即便有 30 s 延迟也被藏在开始之前
- 结论：**不能用这份导出证明手机途径没有延迟**。要直接比较，只能抓手机的蓝牙 HCI 日志（判据文件实验 D）

## 2. 公开报告：这是已知现象，官方没有给出原因

| 来源 | 内容 |
|---|---|
| polar-ble-sdk #424（2023-12，至今开放、0 回复） | Windows C++ 与 Linux Python 两种实现，RR 立即到，ECG「多数时候」晚约 30 s，「有时」立即到 |
| polar-ble-sdk #414（2023-11，已关） | Python + bleak，ECG/ACC 晚 25–30 s，RR 无延迟。Polar 员工答复是「攒满 MTU 缓冲才发」 |
| bleakheart #1（2023-12，已关） | 作者说「相当可预期地」遇到，升级 bleak 到 0.21.1 后在 Linux 上解决；另一人用 0.21.1 仍然有 |
| bleakheart #12（2026-01） | 作者顺带说重连后「ECG 和 ACC 要过一会才开始推流，这不罕见」 |
| polar-ble-sdk KnownIssues.md（API 取得全文） | H10 两条已知问题都与此无关 |

Polar 员工的「MTU 缓冲」解释与本机数据**不符**：本机 MTU 232，ACC 一帧 36 样本在 200 Hz 下 0.18 s 就满；
且首帧传感器时间戳是刚采的（`PMD启动延迟定位.md` 查证 3）——H10 是 30 s 后才开始**采样**，不是攒着没发。
本机 bleak 3.0.2，远新于 0.21.1，「升级 bleak」不适用。

## 3. btsnoop 对比：唯一一次快启动还有第二个差别——**它是首次配对**

| 抓包 | 佩戴 | 建连时状态 | ACC 启动 → 首个 PMD | ACC 启动后观察窗 |
|---|---|---|---|---|
| r2_wifi_off（14:35） | 否 | **未绑定**：连上后 H10 发 Security Req → 现场 SMP 配对（2.06–2.84 s）→ 加密 | **0.32 s** | 约 20 s |
| g5_r1/r2/r3（15:18–15:25） | 否（手指） | 已绑定：建连 0.1 s 即用存储的 LTK 加密 | 无数据 | **22.1–22.7 s** |
| s1_300s（15:32） | 是 | 已绑定，同上 | 29.94 s | 300 s |
| lat1_r1/r2/r3（16:19–16:24） | 是 | 已绑定，同上 | 29.89–30.10 s | 60 s |

- 快启动那次与其余 7 次同时差了两个变量：**佩戴**与**是否已绑定**。此前只归因于「未佩戴」，不完整
- **更正**：15:18 三轮「PMD 0」此前推断为「未佩戴时 H10 不发 PMD」。但那三轮的观察窗只有 22 s，短于 30 s，
  用「已绑定 → 等 30 s」完全可以解释。该推断**没有依据，撤回**
- 两组的 GATT 交互顺序也不同（未绑定时先 MTU 与服务发现、再配对；已绑定时先加密），但进入 PMD 启动时的连接参数最终相同（间隔 0x27、监督超时 6 s）

## 4. 计时起点的线索（推算）

以各次的 LE Connection Complete 为 0：首个 PMD 在 32.39–32.79 s（离散 0.40 s）；以 ACC 启动回应为 0：29.89–30.10 s（离散 0.21 s）。
后者更紧，**倾向**计时从启动命令起算，但两者都只相差约 2.9 s 的固定流程，现有数据分不开 → 判据文件实验 C。

## 现在能说的

- 手机途径是否没有延迟：**未知**，导出文件不含所需信息
- 30 s 的根因：**未知**。领先假设（按证据强弱）：① 与已绑定/加密方式有关 ② 与佩戴有关 ③ 计时起点是启动命令。
  三者都能用单变量实验区分，见 `H10启动延迟_根因判据_测前写定.md`
