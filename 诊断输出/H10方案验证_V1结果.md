### V1-3：字面不满足，是判据措辞缺陷，实际没有中途断开

判据写「日志无 `disconnected`」，但 logger 的断开回调在**正常结束**时也记 `disconnected`（09-28 15:32 那次正常采集同样有），
所以这句字面上任何一轮都满足不了——测前没注意到，是判据写错了，不是数据问题。按判据的本意「全程不断」逐条核：

- 三轮日志事件都只有 `connected → disconnected → end`，`disconnected` 在最后的 ECG/ACC 停止回应之后 2.1–2.5 s
- btsnoop 里是 **Pi 主动**发 Disconnect（0x0406，原因 0x13），完成原因 0x16（本机主机终止），发生在 306.4–306.9 s，即 300 s 采完之后
- 无 `connect_attempt_failed`；第一步判据 2 零缺口也说明中间没断过流

→ 三轮都没有中途断开。V1-3 按本意通过；判据文字应改为「除结束时 Pi 主动断开外无 `disconnected`」，下次（V2）写判据时照此写。

### 判据 5 不通过的原因：检测器按正峰找，这批 ECG 的 R 波是负向的

**以下是看了结果之后做的查证，只解释原因，不改判定。**

判据 5 与判据 3 共用 `h10_parse.py` 的检测器（`find_peaks`，阈值 = 99 分位 × 0.5，只找**正**峰）。0.5–40 Hz 带通后分两个极性数峰：

| 记录 | 时长 | 正向峰（个 / 中位 mV / 每分钟） | 负向峰（个 / 中位 mV / 每分钟） |
|---|---|---|---|
| 手机导出 09-28 08:52 | 34 s | 50 / 0.566 / 88 | 0 |
| Pi 09-28 15:32（第一步） | 300 s | 40 / 0.529 | 364 / 0.732 |
| Pi V1 r1 | 300 s | 217 / 0.197 / 43 | 335 / 0.763 / 67 |
| Pi V1 r2 | 300 s | 264 / 0.196 / 53 | 327 / 0.776 / 65 |
| Pi V1 r3 | 300 s | 75 / 0.223 / 15 | 338 / 0.766 / 68 |

- V1 三轮每分钟负向峰 65–68 个，与 HR 服务心率一致；正向峰数目忽多忽少 → 真正的 R 波是**负向约 0.77 mV**，在判据 5 的 0.3–5 mV 范围内。检测器找到的是 T 波或噪声
- **09-28 15:32 判据 5「通过」（0.861 mV）不可信**：那次检测器只找到 28 个峰（5 分钟应有 300 多拍），这 28 个的中位代表不了 R 波；
  按负向数有 364 个、中位 0.732 mV——结论碰巧落在范围内，但量的不是 R 波
- 所以判据 5 失败与删绑定方案无关，根因和判据 3 相同——检测器。按 V1 结论表属「仅 V1-4 不满足：记录、查原因、不直接判方案失败」
- 附带：`h10_rr_posthoc.py` 在 r3 上分段对齐时报错（某段找不到可比对的窗口），该脚本只是事后探查工具，未修

### 极性：手机导出是正向 R 波，Pi 的四次都是负向（未解释）

只有一份手机导出（09-28 08:52，34 s），与 Pi 的记录不是同一次佩戴。分不开两种可能：
(1) 手机 App 导出时把 ECG 取了反；(2) 那次佩戴方向/位置不同。H10 的 ECG 同一时间只推给一个连接，不能同时对照。
**要分开需做一次：同一次佩戴、不动胸带，先手机录 1 分钟，断开后 Pi 录 1 分钟**，比较极性与幅度。在此之前，`h10_export.py` 导出的 ECG 按 H10 原始符号，不取反。
