# H10 PMD 启动约 30 s 延迟：根因实验判据（测前写定）

写于 2026-09-28，实验之前。依据见 `H10启动延迟_根因排查_现有证据.md`。
延迟定义同前：`h10_start_latency.py` 的 ACC 列（ACC 启动回应 → 首个 ACC 帧，单位 s）。
每轮都用 btmon 抓包，用于核对该轮是否真的发生了 SMP 配对（`h10_btsnoop_timeline.py` 查 `SMP Pairing Req`）。

## 共同条件

- 手机蓝牙关，Pi WiFi 5 GHz，logger 不改（md5 f9f167b6），`--duration 60 --connect-timeout 40`，外层 `timeout -k 10 120`
- 每轮结束 `bluetoothctl disconnect 24:AC:AC:11:CC:D4`，等 10 s

## 实验 A（先做）：删除绑定后首次连接，佩戴

每轮开始前 `bluetoothctl remove 24:AC:AC:11:CC:D4`，让本轮重新配对。连做 3 轮。

| 3 轮 ACC 延迟 | 结论 |
|---|---|
| 3 轮都 < 5 s，且 btsnoop 都有 SMP 配对 | **与已绑定有关**：重新配对的连接快，用存储密钥加密的连接慢 |
| 3 轮都 ≥ 25 s | **与绑定无关**；14:35 的快启动只能归因于未佩戴 → 做实验 B |
| 某轮 btsnoop 没有 SMP 配对 | 该轮作废（绑定没删掉），补做 |
| 其他 | 不判定，记录，加轮 |

## 实验 B：已绑定，不佩戴（带子摘下平放，传感器不接触皮肤），观察窗 60 s

先连一次确保已绑定（实验 A 结束后自然是已绑定）。连做 3 轮。

| 3 轮 ACC 延迟 | 结论 |
|---|---|
| 3 轮都 < 5 s | **与佩戴有关** |
| 3 轮都 ≥ 25 s | **与佩戴无关** |
| 3 轮都 60 s 内无数据 | 不佩戴且已绑定时不推流，记录，不判定 |
| 其他 | 不判定 |

若 A 判「与已绑定有关」，B 仍要做：用来确认 14:35 那次的快是否也有佩戴的成分。

## 实验 C（视 A、B 结果决定）：计时从哪里起算

需要 logger 加「连接后等待 N 秒再发启动命令」的参数，**改动待用户确认**。已绑定、佩戴，N = 20，3 轮。

| 首个 ACC 帧时刻 | 结论 |
|---|---|
| 启动回应后 ≈ 30 s（25–35 s） | 从**启动命令**起算 |
| 连接后 ≈ 32 s（启动回应后 < 15 s） | 从**连接/加密**起算 → 提前连接即可消除 |
| 其他 | 不判定 |

### 实验 C 执行细则（2026-09-29 补写，实验 C 采集之前；上表判据不改）

- 用户 09-29 确认改 logger：加 `--start-delay N`（默认 0，行为与 f9f167b6 相同），部署 md5 **f60a1caf**。
  等待期间只保持连接、HR 已订阅；日志记 `EV start_delay_begin / start_delay_end`
- 前提「已绑定」：实验 A 第 3 轮后没有删绑定，B 没连上，现 Pi 上 Paired/Bonded yes。**每轮不执行 remove**
- 佩戴（实验 B 已证明干放时 H10 不广播）
- 两个量都用 `h10_start_latency.py`：「ACC」列 = 启动回应 → 首个 ACC；「连接→首个ACC s」列 = logger 记的 connected → 首个 ACC
  （logger 的 connected 在 bleak 完成连接之后，比 HCI Connection Complete 晚；不设等待时已绑定为 31.2 s）
- 每轮 btsnoop 里**出现 SMP 配对 → 该轮作废**（说明绑定丢了，不是实验 C 要的条件），补做
- 外层超时改为 `timeout -k 10 150`（多了 20 s 等待）
- 3 轮都落在同一行才下结论；3 轮不一致按「其他」处理

## 实验 E（2026-09-29 写，采集之前）：同一连接内停止再重启，第二次启动快不快

目的：实验 A 的「快」是配对后首次启动才有，还是整个现场配对连接都快。前者意味着「每次删绑定」一旦需要重启 PMD 就失效。

- 用户 09-29 确认。logger 部署 md5 **5d3d1cd6**（旧版备份 `h10_logger.py.bak_f60a1caf`）
- logger 加 `--restart-after S --restart-gap G`（默认 0 = 不重启，行为与 f60a1caf 相同）：首次启动 S 秒后在同一连接内发 ECG、ACC 停止命令，
  等 G 秒再读设置、启动；日志记 `EV restart_begin / restart_end`。停止命令失败 logger 报错退出。取 **S = 45、G = 5**、`--duration 100`、外层 `timeout -k 10 200`
- 两组都佩戴，各 3 轮，先 P 后 B：**P 组**每轮先 `bluetoothctl remove`；**B 组**不 remove（P 组第 3 轮后自然已绑定）
- 判定量：`h10_start_latency.py` 的「重启ACC s」列 = 重启后 ACC 启动回应 → 其后首个 ACC 帧

每轮有效条件（不满足即作废、补做）：
1. 首次启动符合本组条件：P 组「ACC」列 < 5 s 且 btsnoop 有 SMP 配对；B 组 ≥ 25 s 且无 SMP 配对
2. 「停止回应状态」= 00，且「停止后残留PMD」= 0（停止回应 2 s 后到重启回应前无 PMD 帧）
3. 「中途断开」= 否（到重启首帧为止同一连接）

| P 组 3 轮「重启ACC s」 | 结论 |
|---|---|
| 都 < 5 s | 现场配对的连接一直快 → 删绑定在断流重启时仍有效，问题在已绑定连接的状态 |
| 都 ≥ 25 s | 快只出现在配对后首次启动 → 删绑定方案一旦重启 PMD 即失效，**不能作为方案** |
| 其他 | 不判定，加轮 |

| B 组 3 轮「重启ACC s」 | 结论 |
|---|---|
| 都 ≥ 25 s | 已绑定连接每次启动都 30 s，与实验 C 一致 |
| 都 < 5 s | 30 s 是每个连接只发生一次 → 有新绕过法（连上先启停一次），机理仍需继续找 |
| 其他 | 不判定，加轮 |

## 实验 D（手机对照，可选）

「手机途径有没有 30 s」只能这样直接回答：手机开蓝牙 HCI 监听日志（Android 开发者选项「启用蓝牙 HCI 信息收集日志」），
用 Polar App 启动 ECG 记录，导出 btsnoop，用同一个 `h10_btsnoop_timeline.py` 算「启动回应 → 首个 PMD 包」。
判据：< 5 s → 手机途径确实不慢，与 Pi 的差别要在协议交互里找；≥ 25 s → 手机同样有，只是被 App 藏住了。
